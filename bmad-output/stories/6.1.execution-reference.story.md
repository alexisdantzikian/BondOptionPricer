# 6.1: Exécution de référence du notebook

**Story ID:** 6.1
**Epic:** 6 — Cohérence du texte avec les sorties
**Slug:** execution-reference
**PRD :** STORY-004
**Status:** done   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

En tant qu'**auteur du mémoire**,
je veux **une exécution de référence du notebook actuel, avec ses sorties texte et sa durée figées hors du notebook**,
afin de **mesurer ensuite exactement ce que chaque story déplace (GMM, courbe repo de marché) et de vérifier la reproductibilité**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Le notebook `main/oat_option_pricer.ipynb`, dans l'état du commit `HEAD` au démarrage de la story, s'exécute de bout en bout depuis un noyau neuf par `uv run jupyter nbconvert --to notebook --execute --inplace main/oat_option_pricer.ipynb`, sans erreur, avec des compteurs d'exécution séquentiels de 1 au nombre de cellules de code (19 aujourd'hui).
2. Le fichier `bmad-output/reference/sorties_reference.txt` contient, pour chaque cellule de code dans l'ordre, une ligne de repère `=== §<section> | <première ligne non vide de la cellule>` suivie de ses sorties texte (flux `stdout` et `text/plain` des résultats), sans les images.
3. Le script `bmad-output/reference/extraire_sorties.py` produit ce fichier à partir d'un `.ipynb` donné en argument (`uv run python bmad-output/reference/extraire_sorties.py <notebook> > <sortie>`) et peut être réutilisé tel quel par les stories suivantes.
4. Une seconde exécution complète donne des sorties texte identiques à la première (différence vide) ; la comparaison avec les sorties du notebook commité à `HEAD` est faite elle aussi. Toute différence est listée, cellule par cellule, dans `bmad-output/reference/README.md`.
5. `bmad-output/reference/README.md` indique : date d'exécution, hash du commit `HEAD`, commande exacte, durée de chaque exécution complète (secondes), version de Python et nombre de cellules de code ; c'est la référence de NFR-007.
6. À la fin de la story, `git status` ne montre aucune modification de `main/oat_option_pricer.ipynb` ni de `main/main.ipynb` (le notebook ré-exécuté est restauré à `HEAD`).

## Dev Notes

<!-- LOCKED. Concrete guidance compiled from the planning docs WITH SOURCE CITATIONS. -->

- But de la story : figer une exécution de référence avant tout changement, pour mesurer ce que la courbe de marché et la GMM déplacent, et noter la durée d'exécution [Source: prd.md#EPIC-006, STORY-004] [Source: prd.md#NFR-007].
- Aucune modification du notebook n'est livrée par cette story : son périmètre est `bmad-output/reference/` seul [Source: architecture.md#périmètre-de-cellules-par-story-owned-scope].
- Commande d'exécution imposée : `uv run jupyter nbconvert --to notebook --execute --inplace main/oat_option_pricer.ipynb` [Source: architecture.md#ADR-011]. `nbconvert` réécrit le fichier (sorties, métadonnées d'exécution, images PNG ré-encodées) : c'est pourquoi on extrait les sorties texte, puis on restaure le fichier à `HEAD` [Inference].
- Reproductibilité attendue : tout tirage aléatoire du notebook passe par des graines littérales (0 et 1 en §10) ; deux exécutions doivent donner les mêmes sorties texte [Source: prd.md#NFR-003] [Source: architecture.md#ADR-004]. Les images sont exclues de la comparaison car leur encodage peut varier sans que les chiffres changent [Inference].
- État attendu aujourd'hui : 33 cellules dont 19 de code, compteurs 1 → 19, exécution sans erreur lors du dernier commit d5d12cc [Source: bmad-output/context/sharding-context.md#learnings]. Si l'exécution échoue, ne rien corriger dans le notebook : consigner l'erreur dans le README et arrêter la story (le notebook relève d'autres stories) [Inference].
- Repérage des cellules : par section et première ligne, **jamais par indice**, car les stories suivantes insèrent des cellules (§9.3, §9.4, cellule « Chiffres cités ») [Source: architecture.md#ADR-011]. Exemple de repères attendus : `=== §1 | """` (les cellules bibliothèque commencent par une docstring ; prendre alors la première ligne non vide **après** les guillemets si la première ligne est `"""`) [Inference].
- `extraire_sorties.py` n'est **pas** importé par le notebook et vit hors de `main/` : il ne contrevient pas à ADR-001 (aucun `.py` importé par le notebook) [Source: architecture.md#ADR-001]. Il sert au protocole de vérification de toutes les stories suivantes (comparaison des sorties avec la référence) [Source: architecture.md#7-fr--nfr-coverage-matrix, Testing strategy, point 2].
- Durée : mesurer l'exécution complète (horloge murale). Cette valeur est la référence de NFR-007 (≤ 10 minutes visées, aucun ajout ne doit l'allonger de plus de 50 %) et répond à la question Q5 de l'addendum ; l'addendum lui-même n'est pas modifié par cette story [Source: prd.md#NFR-007] [Source: addendum.md#open-questions, Q5].
- Commit : `bmad-output/` n'est pas encore suivi par git (décision de l'auteur en attente). Si `bmad-output/` est suivi au moment de la story, commiter `bmad-output/reference/` avec le message `Référence : exécution du <AAAA-MM-JJ>` ; sinon ne rien commiter et le signaler dans le Dev Agent Record [Inference] [Source: architecture.md#ADR-006]. Jamais de `git push` [Source: architecture.md#ADR-007].
- Environnement : Python 3.12 via `uv`, `jupyter`, `nbconvert`, `nbformat`, `ipykernel` déjà dans `pyproject.toml` ; aucune dépendance à ajouter [Source: architecture.md#8-technology-stack].
